## ۲) راه‌اندازی اولیه سایت (از صفر)

```bash
# ۱. کد را روی سرور بگذارید (از گیت یا زیپ)
cd /var/www
git clone https://github.com/javanbakhthossein-bit/fitup4.git fitup
cd fitup
# (یا زیپ: unzip fitup-deploy-*.zip -d /var/www/fitup)

# ۲. فایل .env بسازید (مقادیر از بخش ۳)
nano .env

# ۳. نصب وابستگی‌ها
bun install

# ۴. دیتابیس
bun run db:generate
bun run db:push        # جداول را می‌سازد (داده‌ای پاک نمی‌شود)

# ۵. بیلد پروداکشن
bun run build

# ۶. آماده‌سازی standalone
mkdir -p .next/standalone/db
cp .env .next/standalone/.env
cp db/custom.db .next/standalone/db/custom.db
cp db/.session-secret .next/standalone/db/.session-secret 2>/dev/null || true

# ۷. اجرا با PM2
pm2 start .next/standalone/server.js --name fitup --update-env
pm2 save && pm2 startup
```

> در آپدیت‌های بعدی فقط: `bash deploy.sh` — همه‌چیز خودکار
> (بکاپ → نصب ffmpeg → db:push → پاک‌سازی stale → build → کپی → pm2 restart → تست سلامت).

### ⚠️ مهم — آپدیت از زیپ: فایل‌های stale را پاک کنید

`unzip` فایل‌هایی را که در نسخه جدید **حذف شده‌اند** پاک نمی‌کند (مثلاً `src/lib/fitness/smart-nav.ts` که در نسخه‌های قدیمی بود و حذف شد — اگر روی سرور بماند، `next build` هنگام TypeScript با خطای تایپ شکست می‌خورد).

از نسخه **v3** به بعد، زیپ فایلی به نام `.deploy-manifest.txt` دارد و `deploy.sh` خودش فایل‌های stale را قبل از build پاک می‌کند — ولی روش مطمئن برای همه نسخه‌ها:

```bash
cd /var/www/fitup
rm -rf src scripts prisma        # فقط پوشه‌هایی که زیپ کامل جایگزین‌شان می‌کند
unzip -o fitup-deploy-*.zip -d /var/www/fitup
bash deploy.sh
```

> ⚠️ هرگز `db/` و `uploads/` و `.env` را پاک/بازنویسی نکنید — دیتای کاربران است.
> (از v3، زیپ دیپلوی **دیگر شامل `db/custom.db` نیست** تا دیتابیس پروداکشن هرگز تصادفی بازنویسی نشود.)

### 🔧 رفع فوری خطای بیلد فعلی (smart-nav.ts)

اگر بیلد با این خطا شکست خورد:
```
./src/lib/fitness/smart-nav.ts:24:17
Type error: Argument of type ... "plans" is not assignable to type 'AppScreen'
```

روی سرور فقط این را بزنید و دوباره دیپلوی کنید:

```bash
cd /var/www/fitup
rm -f src/lib/fitness/smart-nav.ts   # فایل ماندگار از نسخه قدیمی
bash deploy.sh
```

اگر بعد از آن هم خطای تایپ دیگری از فایل دیگری آمد، یعنی stale های بیشتری روی سرور مانده‌اند — روش مطمئن بالا (rm src/scripts/prisma + unzip) را اجرا کنید، یا زیپ **v3** را دیپلوی کنید که خودش پاک‌سازی می‌کند.

### 🔧 رفع فوری خطای بیلد از upload/ (articles-slider-section.tsx)

اگر بیلد با این خطا شکست خورد:
```
./upload/articles-slider-section.tsx:93:10
Type error: Type 'RefObject<HTMLElement | null>' is not assignable...
```

یعنی یک کپی قدیمی از کامپوننت در پوشه `upload/` روی سرور مانده (از نسخه‌های خیلی قدیمی). دو راه:

```bash
# راه ۱ — سریع: فایل‌های کد قدیمی داخل upload/ را پاک کن (دیتابیس/فایل‌های دیگر دست نمی‌خورند)
cd /var/www/fitup
find upload -type f \( -name "*.ts" -o -name "*.tsx" \) -delete
bash deploy.sh
```

```bash
# راه ۲ — قطعی: زیپ v4 را باز کن — tsconfig جدید فقط src/scripts را تایپ‌چک می‌کند
# و deploy.sh خودش فایل‌های کد stale داخل upload/ را پاک می‌کند (قدم ۶-ج)
rm -rf src scripts prisma
unzip -o fitup-deploy-2026-08-31-v4.zip -d /var/www/fitup
bash deploy.sh
```

> از v4، هر فایل .ts/.tsx خارج از src و scripts — در هر پوشه‌ای (upload، backups و…) — دیگر هرگز build را نشکن نمی‌کند. ریشه مشکل: tsconfig قبلی `**/*.ts` داشت؛ یعنی «همه فایل‌های پروژه»؛ tsconfig جدید فقط src/scripts را چک می‌کند.

### Nginx + SSL

```nginx
server {
    listen 443 ssl http2;
    server_name fittup.ir;

    ssl_certificate     /etc/letsencrypt/live/fittup.ir/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/fittup.ir/privkey.pem;

    client_max_body_size 60M;   # آپلود ویدیو ۵۰MB و عکس‌ها

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;     # WebSocket
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;   # پرداخت/تحلیل طولانی
    }
}
```

## ۴) کارهای زمان‌بندی (Cron) — بعد از راه‌اندازی

روی سرور `crontab -e` بزنید و اضافه کنید (CRON_SECRET را جایگزین کنید):

```cron
# یادآورها و چرخه اشتراک‌ها — هر ساعت
0 * * * * curl -s "https://fittup.ir/api/cron/behavioral?secret=CRON_SECRET" > /dev/null

# انتشار مقالات زمان‌بندی‌شده — ⚡ دیگر لازم نیست! ناشر داخلی خودش هر ۱۵ دقیقه اجرا می‌شود
# (اگر خواستید، می‌توانید این cron را هم بگذارید — بی‌ضرر و idempotent است)
# */15 * * * * curl -s "https://fittup.ir/api/cron/publish-scheduled?secret=CRON_SECRET" > /dev/null

# ساخت مقالات زمان‌بندی‌شده سئو — روزانه ۳ بامداد
0 3 * * * curl -s "https://fittup.ir/api/cron/generate-scheduled?secret=CRON_SECRET" > /dev/null

# پاکسازی رسانه‌های قدیمی — روزانه ۴ بامداد
0 4 * * * curl -s "https://fittup.ir/api/cron/cleanup-media?secret=CRON_SECRET" > /dev/null

# بازیابی پرداخت‌های معلق — ⚡ دیگر لازم نیست! جاروی داخلی خودش هر ۱۰ دقیقه اجرا می‌شود
# (اگر خواستید، می‌توانید این cron را هم بگذارید — بی‌ضرر و idempotent است)
# */10 * * * * curl -s "https://fittup.ir/api/cron/recover-payments?secret=CRON_SECRET" > /dev/null
```

> ✅ **v7: جاروی داخلی بازیابی پرداخت‌ها — دیگر به cron خارجی نیاز نیست!**
> خود اپ بعد از هر restart و سپس هر ۱۰ دقیقه، معلق‌ها را با زرین‌پال استعلام و
> در صورت پرداخت، پلن کاربر را خودکار فعال می‌کند (همان route قبلی — از داخل
> پروسه‌ی خود سرور). cron بالا «اختیاری» شده است. خاموش‌کردن:
> `PAYMENT_SWEEP_INTERVAL_MIN=0` در .env
>
> 🔄 **v7: تعیین‌تکلیف آگاهانه پرداخت‌های قدیمی (درخواست مالک: «همه پرداخت‌های
> موفق وریفای شوند»):** معلق‌های قبل از deploy دیگر «کورکورانه» بسته نمی‌شوند —
> هر کدام با استعلام **واقعی** زرین‌پال تعیین‌تکلیف می‌شود:
> • **پرداخت‌شده** (کد 100/101) → همان اولین اجرا: وریفای + فعال‌سازی پلن +
> ثبت تراکنش موفق در حسابداری ✅
> • **پرداخت‌نشده** (پاسخ قطعی منفی) → «منقضی — پرداخت‌نشده» (تمیز، بدون درآمد صوری)
> • **خطای شبکه** → می‌ماند و اجرای بعدی دوباره می‌کوشد
> ادمین همچنان می‌تواند هر ردیف را با دکمه «بازیابی» (حتی در منوی مالی و
> تراکنش‌ها) تعیین‌تکلیف مجدد کند.

### 🔌 راه‌اندازی سرچ کنسول (رفع خطای 403) — قدم‌به‌قدم

خطای «پیکربندی ذخیره شد اما اتصال آزمایشی ناموفق بود: 403» تقریباً همیشه یعنی **قدم ۱ زیر انجام نشده** — پروژه‌ای که سرویس‌اکانت شما در آن ساخته شده (مثل پروژه‌های gen-lang-client که خودکار برای کلید Gemini ساخته می‌شوند) به‌صورت پیش‌فرض فقط Gemini را فعال دارد، نه Search Console API.

1. **فعال‌کردن API (۹۰٪ موارد مشکل همین‌جاست):** `console.cloud.google.com` → بالای صفحه پروژه‌ی سرویس‌اکانت خود را انتخاب کنید (همان پروژه‌ای که ایمیل سرویس‌اکانت به آن ختم می‌شود) → منوی چپ **APIs & Services → Library** → جستجوی «Search Console API» → **Google Search Console API → Enable** → ۱-۲ دقیقه صبر
2. **JSON سرویس‌اکانت:** Credentials → Service Accounts → روی اکانت کلیک → تب **Keys** → Add Key → Create new key → **JSON** (اگر قبلاً دانلود کرده‌اید، همان فایل معتبر است)
3. **دسترسی پراپرتی:** `search.google.com/search-console` → ⚙️ Settings → Users and permissions → **Add user** → ایمیل سرویس‌اکانت (`xxx@yyy.iam.gserviceaccount.com`) → **Restricted** → ~۵ دقیقه صبر (این قدم را قبلاً درست انجام داده‌اید ✓)
4. **در پنل فیتاپ:** پنل ادمین → تب **«سرچ کنسول»** → دکمه پیکربندی → کل فایل JSON را paste کنید + در آدرس سایت فقط `fittup.ir` بنویسید (فرمت دقیق لازم نیست — خودش با پراپرتی گوگل تطبیق و در صورت نیاز اصلاح می‌شود) → «ذخیره و تست اتصال»
5. اگر باز هم خطا داد، پنل دقیقاً می‌گوید مشکل چیست و چه پراپرتی‌هایی در دسترس است؛ بعد از رفع هر قدم در گوگل، دکمه **«تست مجدد اتصال»** را بزنید (بدون paste مجدد JSON)

> 🌐 **خطای ۴۰۳ با صفحه‌ی HTML (Error 403 (Forbidden)!!1) — بلاک IP سرور (رایج در سرورهای ایرانی):**
> اگر پیام خطا با `<!DOCTYPE html>` شروع شود یعنی گوگل IP سرور شما را در ورودی خود محدود کرده است — کلید سرویس‌اکانت شما سالم است (تبادل توکن موفق بوده). راه‌حل: در فایل `.env` سرور:
> ```
> GSC_PROXY_URL=http://user:pass@host:port
> ```
> (پروکسی معتبر خارجی — http یا socks) و سپس `pm2 restart fitup`. از آن پس تمام فراخوانی‌های API گوگل از پروکسی عبور می‌کنند و پنل سرچ کنسول کار می‌کند. بدون پروکسی، بقیه‌ی سایت کاملاً سالم است — فقط داده‌ی سرچ کنسول نمی‌آید.

> ⚠️ تنظیمات بازار کجا است؟ منوی جداگانه‌ای ندارد — در پنل ادمین → تب **«تنظیمات سایت»**: «کد آخرین نسخه اپ بازار» و «کد حداقل نسخه اپ (آپدیت اجباری)» همان تنظیمات بازار هستند. کلید RSA و توکن API بازار طبق `BAZAAR-PUBLISH-GUIDE.md` در `.env` تنظیم می‌شوند.

### تنظیمات پنل ادمین (سایت → ورود ادمین → تنظیمات):

1. **«کد آخرین نسخه اپ بازار»** = آخرین versionCode منتشرشده در بازار (فعلاً ۳ — APK v1.2.0)
2. **«کد حداقل نسخه اپ»** = اگر نسخه‌ای خطرناک بود، این را بالا ببرید → همه کاربران قدیمی آپدیت اجباری می‌گیرند
3. **`bazaar_api_secret`** = توکن «API پیشخان بازار» (برای راستی‌آزمایی خریدهای اپ)
4. **سرچ کنسول** = تب سرچ کنسول: JSON سرویس‌اکانت گوگل + آدرس سایت (راهنمای ۶ قدمی داخل خود تب)

### 🔥 فیکس باگ «پرداخت موفق ولی در پنل در انتظار می‌ماند» (v7 — کامل‌ترین نسخه)

**ریشه باگ** (چیزی که روی سایت قدیمی شما اتفاق می‌افتاد):
1. کاربر در درگاه زرین‌پال پرداخت می‌کرد اما به سایت برنمی‌گشت (موبایل را بست / اینترنت
   قطع شد / سرور در لحظه‌ی verify ری‌استارت شد) → رکورد پرداخت برای همیشه `pending`
   می‌ماند؛ نه پلن فعال می‌شد، نه برنامه ساخته می‌شد، نه مستندات ثبت می‌شد.
2. بدتر: کد ۱۰۱ زرین‌پال («این تراکنش قبلاً verify شده») به‌عنوان replay رد و پرداخت
   failed می‌شد — در حالی که یعنی پول گرفته شده! فقط برخی کاربران شانس می‌آمدند.
3. **حفره‌های v7 (کشف‌شده با کالبدشکافی کامل):**
   - جاروی بازیابی به cron خارجی وابسته بود — اگر ست نشده بود، هیچ‌وقت اجرا نمی‌شد
   - بازیابی موقع لاگین فقط در مسیر `?screen=panel` فعال بود؛ کاربری که فقط صفحه
     اصلی را باز می‌کرد، هرگز بازیابی نمی‌شد
   - **همان لحظه‌ی لاگین موفق** هیچ استعلامی انجام نمی‌شد (تا رفرش بعدی)
   - **رقابت مرگبار UI رسید:** پارامترهای برگشت از بانک در mount حذف می‌شدند →
     صفحه رسید بلافاصله unmount و کاربر لندینگ می‌دید («پرداخت کردم ولی هیچی نشد!»)
   - کاربرِ لاگین‌نشده در صفحه رسید بن‌بست بود (بدون دکمه ورود)
   - منوی «مالی و تراکنش‌ها» فقط استعلام داشت (بدون دکمه بازیابی)

**رفع — شبکه ۷ لایه (v7):**
- **کد ۱۰۱ = پرداخت‌شده** → اگر پرداخت موفق دیگری با همان authority نباشد، پلن تحویل می‌شود
- **خطای شبکه ≠ ناموفق** → claim آزاد می‌شود و بعداً دوباره تلاش می‌شود
- **۱. جاروی داخلی** — داخل خود اپ، بعد از boot و هر ۱۰ دقیقه (بدون نیاز به cron خارجی!)
- **۲. لحظه‌ی لاگین موفق** — استعلام فوری پرداخت‌های معلق کاربر (auth-screen)
- **۳. هر بازدید لاگین‌شده** — حتی لندینگ (throttle ۱۰ دقیقه‌ای)
- **۴. بازگشت از درگاه** — صفحه رسید حالا پایدار است (فیکس race) + دکمه ورود اگر لاگین نیست + تلاش مجدد خودکار
- **۵. ادمین** — دکمه «بازیابی» روی ردیف‌های در انتظار، هم در «حسابداری → پرداخت‌ها» هم در «مالی و تراکنش‌ها» + استعلام actionable
- **۶. شارژ کیف پول معلق** — جارو حالا wallet_topup را هم پوشش می‌دهد (قبلاً فقط پلن‌ها)
- **۷. تعیین‌تکلیف آگاهانه معلق‌های قدیمی** — همان اولین اجرا بعد از deploy: پرداخت‌شده‌ها وریفای و تحویل می‌شوند؛ پرداخت‌نشده‌ها «منقضی — پرداخت‌نشده» می‌شوند

> 💡 برای کاربرانِ قدیمی که الان در سایت قدیمی گیر افتاده‌اند: **هیچ کاری لازم
> نیست** — همان اولین اجرای جاروی داخلی بعد از deploy، همه پرداخت‌های موفقِ معلق
> وریفای، پلن‌شان فعال و در حسابداری ثبت می‌شود (چند ثانیه بعد از بالا آمدن
> سرور، ۴۵ ثانیه تأخیر boot).

## ۹) ورود خودکار کد پیامک در مرورگر (WebOTP) — اختیاری

کاربر اندروید کروم، وقتی کد تأیید می‌رسد، یک پیشنهاد «درج کد» بالای کیبورد می‌بیند و با یک لمس کد در فیلد ورود فیتاپ می‌نشیند (مثل اپ بازار).

**حالت ۱ — پیشنهاد کیبورد اندروید (فعال به‌صورت پیش‌فرض):** فیلد OTP سایت حالا هر مسیر autofill را می‌گیرد و کد در باکس‌ها نمایش داده می‌شود — این حالت کار می‌کند و نیازی به کاری ندارید.

**حالت ۲ — درج خودکار کامل با یک تأیید (WebOTP):** کروم فقط وقتی پیشنهاد «فقط یک لمس» می‌دهد که پیامک حاوی خط `@fittup.ir 1234` باشد. دو راه دارید:
1. **بدون تغییر ارسال:** در پنل sms.ir قالب تأیید را طوری ویرایش کنید که متنش شامل `@fittup.ir {CODE}` باشد (فقط یک‌بار).
2. **ارسال خام (پیشنهادی):** در `.env` مقدار `SMSIR_USE_RAW_SEND=true` بگذارید — پیامک با متن کامل «کد ورود فیتاپ: 1234
@fittup.ir 1234» ارسال می‌شود. ⚠️ نیازمند «خط خدماتی» تأییدشده در پنل sms.ir است (ارسال با متن خام). اگر خط ندارید، همان راه ۱ (ویرایش قالب) کافی است.

## ۶) اپ موبایل و آپدیت‌ها — قواعد

### تغییرات سایت (وب) → بدون آپدیت اپ:
هر تغییری در پنل کاربر، مقالات، قیمت‌ها، قابلیت‌های AI و... فوراً به اپ می‌رسد —
چون اپ یک WebView از سایت است و فایل‌های Next.js هش‌دارند و کش نمی‌شوند.

### تغییرات native → آپدیت اپ لازم است:
- کلید RSA پرداخت بازار
- تغییر دامنه سایت
- قابلیت‌های native جدید (نوتیف، دانلود، چاپ...)

**مراحل آپدیت اپ:**
```bash
cd fitup-bazaar
# ۱. تغییر مورد نظر را در کد اعمال کنید
# ۲. versionCode را +۱ کنید (app/build.gradle.kts)
# ۳. بیلد:
export JAVA_HOME=/مسیر/jdk17
export ANDROID_HOME=/مسیر/android-sdk
./gradlew assembleRelease
# ۴. APK جدید را در پنل بازار آپلود کنید
# ۵. در پنل ادمین سایت: «کد آخرین نسخه اپ» = versionCode جدید
```

کاربران اپ قدیمی: پیام «نسخه جدید در بازار موجود است» می‌بینند؛
اگر «حداقل نسخه» را هم بالا ببرید → دیالوگ غیرقابل‌ردِ آپدیت اجباری.

### نوتیفیکیشن اپ:
- داخل اپ باز: polling سایت هر ۱۰/۳۰ ثانیه → نوتیف سیستم اندروید (خودکار)
- اپ بسته: push از سرویس PWA فقط در مرورگر کار می‌کند؛ برای push اپِ بسته، FCM لازم است
  (اختیاری — در صورت نیاز بعدی اضافه می‌شود؛ اعلان‌های مهم در باز شدن بعدی اپ دیده می‌شوند)
